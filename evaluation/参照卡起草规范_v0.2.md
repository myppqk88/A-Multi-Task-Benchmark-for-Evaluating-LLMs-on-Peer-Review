# 参照卡起草与裁决规范 v0.2（双模型起草，方案 C）

团队于 2026-10-24 决定采用方案 C：**两个不同家族的模型各自独立起草参照卡，再由人工裁决分歧。** 本规范适用于 candidate-v0.2 的全部新卡。预实验的 12 篇论文最先使用本规范。

## 1. 起草者与盲法

| 角色 | 担任者 | 说明 |
|---|---|---|
| 起草者 A | Claude（本仓库协作会话） | 与被测的 Opus 5.5、Sonnet 5.5 同家族 |
| 起草者 B | GPT（团队本地） | 不在被测名单中 |
| 裁决者 | 团队成员 | 看不到每份草稿出自哪个起草者 |

规则：
- 两名起草者使用**完全相同的输入和指令**，彼此看不到对方的草稿。
- 合并工具把两份草稿随机标为 X 和 Y，对照表另行封存，保存在 `pilot/blinding_key.json`，裁决完成前不得打开。
- 每个参照点都记录 `drafted_by`，可取 `X`、`Y` 或 `both`。揭盲后再换回 A 和 B，用于第 6.1 节的偏差检验。

## 2. 起草时可用的材料

| 任务 | 模型可见的材料（判断必须锚定在这里） | 只供起草者参照的材料（`reference_only`） |
|---|---|---|
| T1 | 该题 `input.json` 中的 v1 原稿文本和页面图像 | 针对 v1 的真人报告。只用来定位线索，**每个参照点都必须在原稿中找到依据** |
| T2 | 该题 `input.json` 中的关切和回应 | 无。修订稿和后续评审都不能用来判断回应是否充分 |
| T3 | 该题 `input.json` 中的全部材料，以截止时点为准 | 截止时点之后的报告。只能作为线索，不能作为判定依据 |

```json
  "input_sha256": "...", "card_version": "0.2", "drafter": "X|Y",
  "reference_points": [
    {

      ],
      "match_criteria": "模型的一条论点至少要说出什么，才算命中本点（具体到问题和位置）",
      "acceptable_alternatives": ["本点特有的、合理的不同判断；不得在不同参照点之间复制同一句话"],
      "status": "supported|partly_supported|disputed|unresolved"
    }
  ],
  "label_reference": {
    "primary": "T2/T3 的主判断标签",
    "acceptable_set": ["所有可以接受的标签"],
    "rationale": "为什么这些标签都可接受，其他标签不可接受"
  },
  "known_invalid_patterns": ["本题中典型的错误批评，例如误读某张表、要求作者做本题设定下不可能做的事"],
  "draft_notes": "起草者没能读到或无法判断的内容"

```

L2 整体评分所需的维度锚点沿用 v0.1 的 `dimension_bindings`，留到裁决之后再补写，不在起草阶段写。

## 4. 起草规则

1. **先读完全部真人报告和回应，再读原稿**，然后逐条整理真人关切。一个真人关切对应一个参照点；多位审稿人提出的同一问题，合并为一个参照点，在 `human_sources` 中列出全部来源。
2. **每个参照点必须在模型可见材料中找到依据**，并给出逐字引文或页码。真人提出了、但在材料中找不到依据的关切，标为 `unresolved`，并在 `draft_notes` 中写明原因。
3. **真人可能是错的。** 如果真人关切的前提与原稿不符，仍然要建立参照点，但要把 `status` 标为 `disputed`，并在 `acceptable_alternatives` 中写明"指出这一要求不成立"也是合理的回答。
4. **起草者自己发现的问题**标为 `origin: card_author`。每张卡最多 2 个，并且必须属于 high 或 medium 重要性。它们与真人来源的参照点分开统计。
5. **重要性定义**：
   - `high`：如果成立，就会削弱核心主张，或者使主要结论无法成立；
   - `medium`：影响某个次要结论，或者影响结论的适用范围；
   - `low`：完善性建议。
6. **`match_criteria` 要具体。** 例如写成"指出表 3 中 SD 与 t 值不一致，或指出组间差异检验的统计量与报告数据不符"，而不是"提到统计问题"。
7. **不允许的写法**：用"可能""建议进一步考虑"之类模糊措辞充当判断；不同参照点之间复制同一句话；把作者"已修改"的声明当成事实。

## 5. 合并与裁决流程

1. **合并脚本**：先按真人来源引文重叠、再按原稿引文重叠，把 X 和 Y 两份草稿中的参照点配对。合并结果分成三类：
   - `agreed`：两份都有，且判断一致；
   - `field_conflict`：两份都有，但重要性、类型、状态或标签不同；
   - `X_only` / `Y_only`：只出现在一份草稿中。
2. **裁决表**：每个参照点由裁决者决定"保留 / 修改 / 删除 / 合并"。字段冲突时，选一方的值或改写，并写明理由。T2 和 T3 的 `label_reference` 也要逐项裁决。
3. **第二裁决者**：抽取 20% 的卡，由第二人独立裁决，用来估计裁决本身的一致性。
4. **定稿**：裁决后的卡中，`expert_gold` 仍然为 `null`。`human_review_status` 改为 `team_verified`，同时记录裁决者和日期。
5. **记录**：每张卡都要报告 agreed 的比例、冲突的数量、裁决改动率，以及揭盲后 A 与 B 各自被采纳的比例。

## 6. 产出位置

```text
pilot/
  inputs/<task_id>/input.json        v0.2 输入（模型可见）
  cards_draft/<task_id>/A.json       起草者 A（Claude）
  cards_draft/<task_id>/B.json       起草者 B（GPT）
  merge/<task_id>.json               随机化为 X/Y 后的合并结果
  adjudication/<task_id>.csv         裁决记录
  cards/<task_id>.json               定稿卡
  blinding_key.json                  X/Y 与 A/B 的对照，裁决完成前封存
```
